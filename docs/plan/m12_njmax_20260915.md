# M12：njmax 256 → 512（2026-09-15）

## 发现

M11 因入口机故障失联期间查日志，看到刷屏的：

```
nefc overflow - please increase njmax to 306
```

三轮五列训练全中：

| run | 溢出次数 | 起始 |
|---|---:|---|
| M9（upidjdsa） | 3 900 | — |
| M10（fvhc9ai4） | 32 433 | — |
| M11（1p7x1vsn） | 10 892 | 754 轮（平地热身一结束、第一次踩上五列） |

要求的 njmax 实测 294–402。溢出时约束被丢弃、接触力不可信，**M9/M10/M11 的物理与由它们得出的结论都要打折**，
包括 M10 那组"指令 2.0 下五列全线欠速"的跟踪数据（M11 的 σ 退回 0.5 正是据此做的）。

## 压测方法的教训

`scripts/check_sim_overflow.py` 用 4096 env × 1000–2000 步压，峰值只有 45–68，据此判断 256 够用是错的：
训练是 8192 env × 4 卡跑几千轮，撞到的极端情况远多于压测。而且当时脚本报的 `overflow_worlds` 1–2
在把池放大到 512/128 后仍然出现，被我误判成"与池容量无关"。

**结论：换地形后以真实训练日志里的 `nefc overflow` 为准，压测只能证伪不能证明够用。**
新做法是起训练后先看几百轮日志里有没有这行。

## 改动

`ROUGH_NJMAX` 256 → 512，覆盖实测最大 402 并留余量。`ROUGH_NCONMAX` 维持 64（那一路从未报过溢出）。
代价按注释里的旧记录约每轮 +0.05–0.1 s。

单测 `test_sim_pool_sizes_follow_overflow_measurement` 的参考值改成训练实测上界 402，并把教训写进 docstring。

## 这一轮同时带的改动

M11 的 σ_move 0.5（commit df3f145）保留在内——它的依据虽然来自坏物理下的测量，但 σ=1.0 让中高速段
奖励落差只有两成这个算术是与物理无关的，退回 0.5 仍然成立。M12 = M11 + njmax 512，相对 M11 是单变量。
